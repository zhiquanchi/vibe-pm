> 审查日期：2026-08-12  
> 审查范围：开发管理总纲及 PRD-01 至 PRD-07  
> 审查视角：产品定位、用户价值、体验设计

## 一、总体评价

**✅ 通过：产品方向清晰，核心价值主张成立，所有关键用户体验决策已锁定。**

产品以"开发阶段"作为组织骨架、用验收闭环替代 Scrum 仪式、AI 副驾驶辅助决策的定位具有差异化。目标用户（3-20人研发团队）与功能范围匹配。原先的 3 个 P0 级问题和 5 个 P1 级问题均已通过产品决策确认解决方案，可以进入开发阶段。

---

## 二、产品优势

### 1. 差异化定位清晰
不强制 Scrum、不要求故事点和 Sprint 规划，以"开发阶段"为核心组织项目，符合中小团队希望"有结构但不重仪式"的实际需求。与 Jira、Linear、Teambition 等工具形成明确差异。

### 2. 闭环机制完整
从阶段定义 → 任务执行 → 依赖/阻塞管理 → 交付物提交 → 验收确认的完整闭环，确保"阶段完成"有可验证标准，而非仅靠主观判断。

### 3. AI 副驾驶价值明确
PRD-07 将 AI 定位为"信息整理与风险识别助手"而非"自动决策者"，既提供价值又不越权，符合项目管理场景的责任边界要求。

### 4. 权限模型简洁实用
项目负责人、阶段负责人、成员、观察者四类角色覆盖核心协作场景，避免过度复杂的自定义权限配置。

## 三、产品问题

### 🔴 P0 级：影响首版核心体验

#### P0-01：任务"待确认"状态的业务逻辑未在 PRD 中明确定义

**问题描述**  
总纲定义任务状态为 `未开始 → 进行中 ↔ 受阻 → 待确认 → 已完成`，但 PRD-03 和 PRD-04 没有完整说明"待确认"的触发场景、确认责任和状态流转规则。

**实际业务逻辑（已与产品确认）**  
"待确认"状态用于阻塞解除后的二次确认流程：

1. **触发场景：** 任务执行方遇到问题，标记任务为"受阻"并指定处理人
2. **解除阻塞：** 处理人解决问题后填写解决结果，任务自动进入"待确认"状态
3. **任务负责人确认：** 原执行者验证问题已解决，决定继续执行或标记新阻塞
4. **确认后恢复：** 确认无问题后任务回到"进行中"状态

**完整状态循环（正常且必要）**  
```
进行中 → 受阻（执行者标记）→ 待确认（处理人解除阻塞）→ 进行中（执行者确认）
       ↑                                                    ↓
       └──────────────────── 发现新问题，标记新阻塞 ─────────┘
```

**PRD 缺失内容**  
1. **总纲需补充任务状态转换表：**
   
   | 当前状态 | 触发事件 | 操作者 | 前置条件 | 目标状态 |
   |---------|---------|--------|---------|---------|
   | 进行中 | 标记阻塞 | 任务负责人/阶段负责人 | 必须填写原因和处理人 | 受阻 |
   | 受阻 | 解除阻塞 | 阻塞处理人 | 必须填写解决结果 | 待确认 |
   | 待确认 | 确认可继续 | 任务负责人 | 无 | 进行中 |
   | 待确认 | 标记新阻塞 | 任务负责人 | 必须填写新原因和处理人 | 受阻 |

2. **PRD-04 需补充用户故事 US-005：**
   ```
   US-005：确认阻塞已解除
   
   Description: 作为任务负责人，我希望在处理人解除阻塞后确认问题已解决，
   以便决定是否继续执行或标记新问题。
   
   Acceptance Criteria:
   - [ ] 处理人解除阻塞后，任务自动进入"待确认"状态
   - [ ] 任务负责人在任务详情中看到"待确认"状态和处理人的解决结果
   - [ ] 任务负责人可选择"确认继续"或"标记新阻塞"
   - [ ] 选择"确认继续"后任务恢复到"进行中"状态
   - [ ] 选择"标记新阻塞"时必须填写新的阻塞原因和处理人
   - [ ] 首版不要求实时通知，任务负责人通过"我的任务"或项目总览发现待确认任务
   - [ ] 在浏览器中验证解除→待确认→继续和解除→待确认→新阻塞两条路径
   ```

**建议**  
PM 需在总纲补充完整状态转换表，并在 PRD-04 补充 US-005，明确"待确认"不是任务完成前的审核，而是阻塞解除后的确认机制。

#### P0-02：阶段工作台首版视图已确定为列表

**产品决策（已确认）**  
首版阶段工作台使用**列表视图**。

**决策理由**  
- 列表视图支持更高的信息密度，适合快速扫描任务
- 支持更丰富的筛选维度（标题、负责人、状态、优先级、计划日期）
- 与"我的任务"跨项目视图保持一致的交互模式
- 批量操作和排序功能更容易实现

**PRD 需更新内容**

   - [ ] 每行展示任务标题、负责人、优先级、计划日期、状态
   - [ ] 支持按标题、负责人、状态、优先级筛选
   - [ ] 支持按创建时间、计划日期、优先级排序
   - [ ] 点击任务行展开详情或进入任务详情页
   - [ ] 已完成阶段的任务列表为只读

#### P0-03：验收职责要求项目必须有两名项目负责人

**产品决策（已确认）**  
项目必须至少有**两名项目负责人**，一名身份为 PM（产品/项目经理），一名为执行者（技术负责人/开发负责人）。

**决策理由**  
- 确保阶段验收的独立性：提交人与验收人分离，避免自验收
- 符合软件开发项目的常见角色配置：PM 负责需求和验收，Tech Lead 负责执行
- 小团队（3-5人）通常也会有明确的 PM 和 Tech Lead 角色

**PRD 需更新内容**  

1. **PRD-02 补充项目创建约束：**
   ```
   US-002：管理项目成员（补充）
   
   Acceptance Criteria:
   - [ ] 创建项目时必须指定至少两名项目负责人
   - [ ] 建议在创建向导中提示"指定 PM 和技术负责人"
   - [ ] 项目负责人总数不能少于 2 人
   - [ ] 移除项目负责人时，若剩余不足 2 人则阻止操作并提示
   - [ ] 错误提示："项目至少需要 2 名项目负责人以确保验收独立性"
   ```

2. **PRD-05 明确验收规则：**
   ```
   验收职责矩阵：
   
   | 提交人身份 | 可处理验收的人 | 不可处理验收的人 |
   |-----------|--------------|----------------|
   | 阶段负责人（非项目负责人） | 任一项目负责人 | 提交人本人 |
   | 项目负责人A | 另一项目负责人B/C/... | 提交人A本人 |
   
   前置条件：
   - 项目至少有 2 名项目负责人（创建时强制）
   - 阶段负责人可以是项目负责人之一
   ```

3. **PRD-02 开放问题删除：** 移除关于"单一项目负责人"的场景讨论

4. **总纲成功标准补充：** "100% 的项目具有至少 2 名项目负责人"

**对小团队的影响**  
- 3 人团队需明确指定 2 人为项目负责人（如 PM + Tech Lead）
- 第 3 人可以是成员或观察者角色
- 符合实际协作场景，不会增加额外负担

### 🟠 P1 级：影响用户体验与认知

#### P1-01：主阶段与并行阶段已明确定义

**产品决策（已确认）**  
采用**方案 C：灵活的视觉优先级标识**

**定义：**
- **主阶段** = 当前最重要的推进方向，在总览、风险提示、AI 摘要中优先展示
- **并行阶段** = 同时进行的其他工作（可能是提前启动的下游阶段，也可能是辅助/独立工作）
- 所有阶段地位平等，主阶段只是视觉和信息优先级的标识
- 项目负责人可以随时切换主阶段

**典型场景举例：**
```
同一时间：
  主阶段：开发（核心功能开发）
  并行阶段：
    - 测试（提前启动，准备测试用例）
    - 文档编写（辅助工作）
    - 技术预研（独立工作）
```

**PRD 需补充内容：**
- 总纲或 PRD-01 明确主阶段的视觉优先级：在项目总览、风险区、AI 摘要中优先展示
- PRD-06 明确主阶段在总览页面的展示位置和样式
- PRD-07 明确 AI 副驾驶优先分析主阶段的风险和进度

---

#### P1-02：任务优先级枚举已确定为国际化方案

**产品决策（已确认）**  
使用 **i18n 国际化，中文环境默认显示中文优先级**

**枚举定义：**
- **紧急**（Critical）：阻断性任务，必须立即处理
- **重要**（High）：高优先级任务，优先安排
- **正常**（Medium）：常规任务，默认优先级
- **低**（Low）：低优先级任务，可延后处理

**相关规则：**
- 新建任务默认优先级为"正常"
- PRD-06 风险区展示的"高优先级任务阻塞"指"紧急"和"重要"两个级别
- 支持按优先级筛选和排序

**PRD 需补充内容：**
- 总纲定义完整的优先级枚举和中英文对照
- PRD-03 更新"默认优先级为 P2"改为"默认优先级为正常"
- PRD-06 明确"高优先级"指"紧急"和"重要"

#### P1-03：项目整体状态采用系统自动计算

**产品决策（已确认）**  
项目整体状态由**系统根据主阶段状态自动计算**

**状态映射规则：**
- 主阶段为"进行中" → 项目整体状态显示"进行中"
- 主阶段为"受阻" → 项目整体状态显示"受阻"
- 主阶段为"待验收" → 项目整体状态显示"待验收"
- 所有阶段均为"已完成" → 项目整体状态显示"已完成"
- 所有阶段均为"未开始" → 项目整体状态显示"未开始"

**优点：**
- 实时反映项目真实状态，无需手动维护
- 与主阶段概念一致，降低认知负担
- 避免人工标记遗漏更新的问题

**PRD 需补充内容：**
- PRD-06 US-001 明确整体状态的计算规则
- 总纲补充项目状态与主阶段状态的映射关系

#### P1-04：删除对象策略采用严格阻止

**产品决策（已确认）**  
被依赖或有关联的对象采用**严格阻止删除**策略

**具体规则：**

| 删除对象 | 阻止条件 | 错误提示 | 解决方式 |
|---------|---------|---------|---------|
| 任务 | 被其他任务依赖 | "该任务被 X 个任务依赖，请先解除依赖关系" | 逐一解除依赖关系 |
| 任务 | 是阶段验收必需任务 | "该任务是阶段验收必需项，请先调整验收条件" | 在验收条件中移除 |
| 阶段 | 包含已完成的任务 | "该阶段包含已完成任务，无法删除" | 不可删除 |
| 阶段 | 包含未完成的任务 | "该阶段包含 X 个未完成任务，请先移动或删除任务" | 清空阶段任务 |
| 成员 | 是项目负责人且只剩一人 | "项目至少需要 2 名项目负责人" | 先添加新负责人 |
| 成员 | 是阶段负责人 | "该成员是 X 个阶段的负责人，请先更换负责人" | 逐一更换负责人 |
| 成员 | 有未完成任务 | "该成员有 X 个未完成任务，请先重新分配" | 重新分配任务 |

**允许删除的情况：**
- 空阶段（无任务、无交付物）
- 未被依赖且非验收必需的任务
- 无负责阶段、无未完成任务的成员

**PRD 需补充内容：**
- 总纲补充完整的删除策略表
- PRD-01/02/03 各自明确阻止条件和错误提示文案

#### P1-05：AI 副驾驶采用实时数据读取

**产品决策（已确认）**  
AI 副驾驶**实时读取项目数据，不展示时间戳**

**实现方式：**
- 用户每次触发 AI 生成（项目摘要、风险分析、问答）时，直接查询最新项目数据
- 结果始终基于当前项目状态，无延迟
- 不需要展示"数据截止时间"或"数据更新于 X 分钟前"

**优点：**
- 用户信任度高，数据始终准确
- 无需维护缓存刷新逻辑
- 用户体验简洁，无需理解"数据时效性"概念

**性能考虑：**
- 首版项目规模较小（3-20人团队），实时查询性能可接受
- 若后续出现性能问题，可在后台优化查询效率，但对用户仍保持"实时"体验

**PRD 需更新内容：**
- PRD-07 删除所有关于"数据截止时间"的验收标准
- PRD-07 US-001 移除"用户可重新生成摘要，并看到摘要所依据的项目数据截止时间"
- PRD-07 US-004 移除"回答明确标注适用的项目、阶段和数据截止时间"中的时间戳部分
- PRD-07 FR-14 删除"系统必须展示 AI 输出所依据的项目数据截止时间"

### 🟢 P2 级：可后续优化

#### P2-01：缺少"批量操作"场景

首版不支持批量移动任务、批量修改优先级、批量分配负责人，对于 20 人团队可能操作效率较低。建议在 Future 中明确列出。

#### P2-02："我的任务"缺少"今日计划"视图

PRD-03 US-005 提供跨项目未完成任务视图，但缺少"今天应该做什么"的快速入口。建议补充按计划日期筛选的默认视图。

#### P2-03：活动记录不支持"@提及"或"关注"

PRD-06 提供活动记录，但用户无法订阅特定阶段或任务的变化通知，依赖手动刷新。可作为 Future 功能。

## 五、产品建议

### 建议 1：明确首版"最小可用"边界

当前 PRD 已有较完整的非目标列表，但建议补充"首版可以不完美但必须可用"的具体标准：
- 任务状态流转必须完整（P0-01）
- 验收流程必须在所有团队规模下可用（P0-03）
- 工作台视图必须锁定（P0-02）

### 建议 2：补充关键用户场景的操作路径图

建议在总纲补充 3-5 个典型用户旅程的页面跳转路径，例如：
```
场景：处理受阻任务
路径：项目总览 → 风险区"3个受阻任务" → 任务详情 → 解除阻塞 → 填写解决结果 → 返回项目总览
```

### 建议 3：AI 副驾驶首版聚焦"状态理解"而非"行动建议"

PRD-07 已包含状态摘要、风险分析、行动建议、问答四类功能，建议首版聚焦前两项（状态摘要 + 风险分析），行动建议和问答作为 v1.1 功能，以降低首版复杂度。
