# Vibe PM PRD 产品审查报告

> 审查日期：2026-08-12  
> 审查范围：开发管理总纲及 PRD-01 至 PRD-07  
> 审查视角：产品定位、用户价值、体验设计  
> 审查模式：仅产品维度，不涉及商业、实现与技术

## 一、总体评价

**🟡 有条件通过：产品方向清晰，核心价值主张成立，但关键用户体验决策点仍未锁定。**

产品以"开发阶段"作为组织骨架、用验收闭环替代 Scrum 仪式、AI 副驾驶辅助决策的定位具有差异化。目标用户（3-20人研发团队）与功能范围匹配。但部分用户旅程的关键体验节点（如工作台视图、任务状态确认流程）尚未明确，会影响首版用户认知与操作流畅度。

---

## 二、产品优势

### 1. 差异化定位清晰
不强制 Scrum、不要求故事点和 Sprint 规划，以"开发阶段"为核心组织项目，符合中小团队希望"有结构但不重仪式"的实际需求。与 Jira、Linear、Teambition 等工具形成明确差异。

### 2. 闭环机制完整
从阶段定义 → 任务执行 → 依赖/阻塞管理 → 交付物提交 → 验收确认的完整闭环，确保"阶段完成"有可验证标准，而非仅靠主观判断。

### 3. AI 副驾驶价值明确
PRD-07 将 AI 定位为"信息整理与风险识别助手"而非"自动决策者"，既提供价值又不越权，符合项目管理场景的责任边界要求。

### 4. 权限模型简洁实用
项目负责人、阶段负责人、成员、观察者四类角色覆盖核心协作场景，避免过度复杂的自定义权限配置。

## 三、产品问题

### 🔴 P0 级：影响首版核心体验

#### P0-01：任务"待确认"状态的业务逻辑未在 PRD 中明确定义

**问题描述**  
总纲定义任务状态为 `未开始 → 进行中 ↔ 受阻 → 待确认 → 已完成`，但 PRD-03 和 PRD-04 没有完整说明"待确认"的触发场景、确认责任和状态流转规则。

**实际业务逻辑（已与产品确认）**  
"待确认"状态用于阻塞解除后的二次确认流程：

1. **触发场景：** 任务执行方遇到问题，标记任务为"受阻"并指定处理人
2. **解除阻塞：** 处理人解决问题后填写解决结果，任务自动进入"待确认"状态
3. **任务负责人确认：** 原执行者验证问题已解决，决定继续执行或标记新阻塞
4. **确认后恢复：** 确认无问题后任务回到"进行中"状态

**完整状态循环（正常且必要）**  
```
进行中 → 受阻（执行者标记）→ 待确认（处理人解除阻塞）→ 进行中（执行者确认）
       ↑                                                    ↓
       └──────────────────── 发现新问题，标记新阻塞 ─────────┘
```

**PRD 缺失内容**  
1. **总纲需补充任务状态转换表：**
   
   | 当前状态 | 触发事件 | 操作者 | 前置条件 | 目标状态 |
   |---------|---------|--------|---------|---------|
   | 进行中 | 标记阻塞 | 任务负责人/阶段负责人 | 必须填写原因和处理人 | 受阻 |
   | 受阻 | 解除阻塞 | 阻塞处理人 | 必须填写解决结果 | 待确认 |
   | 待确认 | 确认可继续 | 任务负责人 | 无 | 进行中 |
   | 待确认 | 标记新阻塞 | 任务负责人 | 必须填写新原因和处理人 | 受阻 |

2. **PRD-04 需补充用户故事 US-005：**
   ```
   US-005：确认阻塞已解除
   
   Description: 作为任务负责人，我希望在处理人解除阻塞后确认问题已解决，
   以便决定是否继续执行或标记新问题。
   
   Acceptance Criteria:
   - [ ] 处理人解除阻塞后，任务自动进入"待确认"状态
   - [ ] 任务负责人在任务详情中看到"待确认"状态和处理人的解决结果
   - [ ] 任务负责人可选择"确认继续"或"标记新阻塞"
   - [ ] 选择"确认继续"后任务恢复到"进行中"状态
   - [ ] 选择"标记新阻塞"时必须填写新的阻塞原因和处理人
   - [ ] 首版不要求实时通知，任务负责人通过"我的任务"或项目总览发现待确认任务
   - [ ] 在浏览器中验证解除→待确认→继续和解除→待确认→新阻塞两条路径
   ```

**建议**  
PM 需在总纲补充完整状态转换表，并在 PRD-04 补充 US-005，明确"待确认"不是任务完成前的审核，而是阻塞解除后的确认机制。

#### P0-02：阶段工作台首版视图已确定为列表

**产品决策（已确认）**  
首版阶段工作台使用**列表视图**。

**决策理由**  
- 列表视图支持更高的信息密度，适合快速扫描任务
- 支持更丰富的筛选维度（标题、负责人、状态、优先级、计划日期）
- 与"我的任务"跨项目视图保持一致的交互模式
- 批量操作和排序功能更容易实现

**PRD 需更新内容**  
1. **PRD-03 US-002 需明确列表视图的验收标准：**
   ```
   US-002：查看阶段任务工作台（列表视图）
   
   Acceptance Criteria:
   - [ ] 工作台以列表形式展示未开始、进行中、受阻、待确认和已完成任务
   - [ ] 每行展示任务标题、负责人、优先级、计划日期、状态
   - [ ] 支持按标题、负责人、状态、优先级筛选
   - [ ] 支持按创建时间、计划日期、优先级排序
   - [ ] 点击任务行展开详情或进入任务详情页
   - [ ] 已完成阶段的任务列表为只读
   - [ ] 在桌面和窄屏浏览器中验证有数据、空状态和只读状态
   ```

2. **PRD-03 开放问题删除：** 移除"首版阶段工作台采用列表还是看板作为唯一主视图？"

3. **总纲或 PRD-03 明确 Future：** 看板视图作为 v1.1 或 v2.0 功能，提供状态流转可视化和拖拽操作

#### P0-03：验收职责要求项目必须有两名项目负责人

**产品决策（已确认）**  
项目必须至少有**两名项目负责人**，一名身份为 PM（产品/项目经理），一名为执行者（技术负责人/开发负责人）。

**决策理由**  
- 确保阶段验收的独立性：提交人与验收人分离，避免自验收
- 符合软件开发项目的常见角色配置：PM 负责需求和验收，Tech Lead 负责执行
- 小团队（3-5人）通常也会有明确的 PM 和 Tech Lead 角色

**PRD 需更新内容**  

1. **PRD-02 补充项目创建约束：**
   ```
   US-002：管理项目成员（补充）
   
   Acceptance Criteria:
   - [ ] 创建项目时必须指定至少两名项目负责人
   - [ ] 建议在创建向导中提示"指定 PM 和技术负责人"
   - [ ] 项目负责人总数不能少于 2 人
   - [ ] 移除项目负责人时，若剩余不足 2 人则阻止操作并提示
   - [ ] 错误提示："项目至少需要 2 名项目负责人以确保验收独立性"
   ```

2. **PRD-05 明确验收规则：**
   ```
   验收职责矩阵：
   
   | 提交人身份 | 可处理验收的人 | 不可处理验收的人 |
   |-----------|--------------|----------------|
   | 阶段负责人（非项目负责人） | 任一项目负责人 | 提交人本人 |
   | 项目负责人A | 另一项目负责人B/C/... | 提交人A本人 |
   
   前置条件：
   - 项目至少有 2 名项目负责人（创建时强制）
   - 阶段负责人可以是项目负责人之一
   ```

3. **PRD-02 开放问题删除：** 移除关于"单一项目负责人"的场景讨论

4. **总纲成功标准补充：** "100% 的项目具有至少 2 名项目负责人"

**对小团队的影响**  
- 3 人团队需明确指定 2 人为项目负责人（如 PM + Tech Lead）
- 第 3 人可以是成员或观察者角色
- 符合实际协作场景，不会增加额外负担

### 🟠 P1 级：影响用户体验与认知

#### P1-01：主阶段与并行阶段的用户价值不够清晰

**问题描述**  
PRD-01 引入"主阶段"和"并行阶段"概念，但没有说明：
- 用户为什么需要区分"主"与"并行"
- "主阶段"在产品中有什么特殊权限或视觉优先级
- 切换主阶段的典型场景是什么

**用户影响**  
- 用户不理解为什么不能多个阶段并行推进且地位平等
- "主阶段"可能被误解为"当前唯一可以工作的阶段"

**建议**  
在总纲或 PRD-01 补充：
- 主阶段的用户价值：帮助团队明确"当前最重要的推进方向"，在总览、风险提示、AI 摘要中优先展示
- 典型场景举例：开发阶段为主阶段，测试阶段并行进行；当开发完成后切换测试为主阶段

---

#### P1-02：任务优先级枚举未定义

**问题描述**  
PRD-03 提到"默认优先级为 P2"，PRD-06 提到"高优先级任务阻塞"，但没有定义完整优先级枚举（P0/P1/P2/P3？Critical/High/Medium/Low？）。

**用户影响**  
- 用户不知道优先级有哪些选项
- "高优先级"的边界不清晰（P0 和 P1 都算高？还是只有 P0？）
- 影响风险展示逻辑与用户预期

**建议**  
在总纲定义优先级枚举，推荐：
- P0（紧急）、P1（重要）、P2（正常）、P3（低优先级）
- 明确"高优先级"指 P0 和 P1

---

#### P1-03：项目"整体状态"未定义

**问题描述**  
PRD-06 US-001 要求"总览展示项目名称、负责人、计划日期和整体状态"，但没有定义"整体状态"是什么。

**用户影响**  
- 用户不知道项目整体状态有哪些可能值（正常/风险/延期/暂停？）
- 不清楚整体状态是人工标记还是系统自动计算
- 与阶段状态、任务状态的关系不明确

**建议**  
明确两种选项之一：
- **选项A**：整体状态由项目负责人手动标记（如"正常推进""存在风险""已暂停"）
- **选项B**：整体状态由系统根据阶段、阻塞、逾期自动计算（如"进行中""受阻""已完成"）

---

#### P1-04：删除对象的影响范围只"展示"不阻止，用户易误操作

**问题描述**  
多处 PRD 提到"删除前展示影响范围"（PRD-01 删除阶段、PRD-03 删除任务、PRD-02 移除成员），但没有明确是：
- 展示影响后仍允许删除（级联删除或解绑）
- 展示影响后阻止删除

**用户影响**  
- 用户可能误以为"展示影响"只是提示，实际删除后导致数据丢失
- 被依赖任务、必需交付物、负责人被删除后，依赖关系、验收条件会变成孤儿引用

**建议**  
在总纲明确删除策略：
- **被依赖任务删除**：阻止删除，要求先解除依赖关系
- **阶段负责人移除**：阻止移除，要求先更换负责人
- **包含已完成任务的阶段删除**：阻止删除
- **空阶段删除**：允许删除

---

#### P1-05：AI 副驾驶的"项目数据截止时间"用户价值不明确

**问题描述**  
PRD-07 US-001、US-004 要求"展示 AI 输出所依据的项目数据截止时间"，但没有说明：
- 这是为了解决什么问题（数据缓存？异步生成？）
- 用户看到"截止时间"后应该做什么

**用户影响**  
- 用户可能误以为数据不实时，对 AI 产生不信任
- 若数据实时，展示"截止时间"反而增加认知负担

**建议**  
- 若 AI 基于实时数据，不需要展示截止时间
- 若 AI 基于快照或缓存，改为展示"数据更新于 X 分钟前"并提供"刷新"按钮

### 🟢 P2 级：可后续优化

#### P2-01：缺少"批量操作"场景

首版不支持批量移动任务、批量修改优先级、批量分配负责人，对于 20 人团队可能操作效率较低。建议在 Future 中明确列出。

#### P2-02："我的任务"缺少"今日计划"视图

PRD-03 US-005 提供跨项目未完成任务视图，但缺少"今天应该做什么"的快速入口。建议补充按计划日期筛选的默认视图。

#### P2-03：活动记录不支持"@提及"或"关注"

PRD-06 提供活动记录，但用户无法订阅特定阶段或任务的变化通知，依赖手动刷新。可作为 Future 功能。

## 五、产品建议

### 建议 1：明确首版"最小可用"边界

当前 PRD 已有较完整的非目标列表，但建议补充"首版可以不完美但必须可用"的具体标准：
- 任务状态流转必须完整（P0-01）
- 验收流程必须在所有团队规模下可用（P0-03）
- 工作台视图必须锁定（P0-02）

### 建议 2：补充关键用户场景的操作路径图

建议在总纲补充 3-5 个典型用户旅程的页面跳转路径，例如：
```
场景：处理受阻任务
路径：项目总览 → 风险区"3个受阻任务" → 任务详情 → 解除阻塞 → 填写解决结果 → 返回项目总览
```

### 建议 3：AI 副驾驶首版聚焦"状态理解"而非"行动建议"

PRD-07 已包含状态摘要、风险分析、行动建议、问答四类功能，建议首版聚焦前两项（状态摘要 + 风险分析），行动建议和问答作为 v1.1 功能，以降低首版复杂度。

## 七、附加观察

### 优点
- PRD 结构化程度高，每个模块都有明确的用户故事与验收标准
- 非目标定义清晰，避免范围蔓延
- 权限边界明确，不越权设计
- AI 定位克制，不过度承诺

### 改进空间
- 部分用户故事的"为什么"（用户价值）可以更明确
- 缺少产品原型或线框图辅助理解交互流程
- 成功指标部分依赖主观判断（如"可理解的中文错误"）

---

## 八、结论

**产品方向成立，核心价值清晰，但需锁定 6 项关键用户体验决策后方可进入开发。**

建议产品经理在 48 小时内完成《产品决策清单》中的 6 项决策，并更新总纲与对应子 PRD，确保开发团队有明确、无歧义的产品契约。
