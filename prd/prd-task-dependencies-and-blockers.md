# PRD-04：任务依赖与阻塞

> 版本：v1.0 Draft  
> 日期：2026-08-07  
> 状态：待评审  
> 上游依赖：PRD-03 阶段任务管理

## 1. 概述

允许团队表达任务前置关系，并记录任务或阶段无法继续推进的具体原因、处理人和解决结果。

## 2. 目标

- 用户能够区分“尚未开始”和“因条件不满足无法继续”。
- 循环依赖在写入前被阻止。
- 所有未解除阻塞都能被项目负责人发现并追踪。

## 3. 用户故事

### US-001：设置任务前置依赖

**Description:** 作为研发成员，我希望设置任务的前置任务，以便说明执行顺序和等待条件。

**Acceptance Criteria:**

- [ ] 用户可为任务选择一个或多个同项目任务作为前置任务。
- [ ] 任务不能依赖自身。
- [ ] 系统拒绝直接或间接循环依赖并说明依赖路径。
- [ ] 任务详情展示全部未完成前置任务。
- [ ] 依赖变化生成活动记录。
- [ ] 在浏览器中验证单个、多个和循环依赖。

### US-002：处理未完成依赖

**Description:** 作为任务负责人，我希望看到未满足依赖的提示，以便判断是否可以开始工作。

**Acceptance Criteria:**

- [ ] 前置任务未完成时显示明确风险提示。
- [ ] 用户可以在确认提示后开始存在未完成依赖的任务。
- [ ] 系统不得因前置任务完成而自动完成后置任务。
- [ ] 前置任务完成后，后置任务的未满足依赖提示立即更新。
- [ ] 删除被依赖任务前展示受影响的后置任务。
- [ ] 在浏览器中验证提示、确认和依赖解除。

### US-003：标记和解除任务阻塞

**Description:** 作为任务负责人，我希望记录任务阻塞，以便团队协助解决问题。

**Acceptance Criteria:**

- [ ] 将任务设为受阻时必须填写原因和处理人。
- [ ] 阻塞记录保存创建人和创建时间。
- [ ] 解除阻塞时必须填写解决结果。
- [ ] 解除后任务恢复到阻塞前状态。
- [ ] 历史阻塞记录保留且不可由普通成员删除。
- [ ] 在浏览器中验证标记、解除和历史记录。

### US-004：标记和解除阶段阻塞

**Description:** 作为阶段负责人，我希望记录阶段级阻塞，以便表达影响整个阶段的问题。

**Acceptance Criteria:**

- [ ] 阶段负责人或项目负责人可将活动阶段设为受阻。
- [ ] 阶段阻塞必须填写原因和处理人。
- [ ] 阶段受阻不会自动修改阶段内任务状态。
- [ ] 解除阻塞后阶段恢复到受阻前状态。
- [ ] 未解除阶段阻塞会阻止提交阶段验收。
- [ ] 在浏览器中验证阶段阻塞和任务状态独立性。

## 4. 功能需求

- FR-1：系统必须允许任务依赖同项目的一个或多个任务。
- FR-2：系统必须拒绝自依赖和循环依赖。
- FR-3：系统必须展示任务未完成的前置依赖。
- FR-4：系统必须在强制开始有未完成依赖的任务前请求确认。
- FR-5：系统必须在创建阻塞时要求原因和处理人。
- FR-6：系统必须保存阻塞创建与解除记录。
- FR-7：系统必须将任务和阶段阻塞状态分别管理。
- FR-8：系统必须阻止存在未解除阶段阻塞的阶段提交验收。

## 5. 非目标

- 不自动计算关键路径或重新排期。
- 不根据依赖自动改变任务状态。
- 不实现跨项目任务依赖。
- 不向外部即时通讯工具推送阻塞通知。

## 6. 技术考虑

- 循环依赖校验必须覆盖任意深度的间接路径。
- 任务依赖和阻塞变更需与活动记录在同一事务内保存。
- 删除任务前必须在服务端查询并返回受影响关系。

## 7. 成功指标

- 写入循环依赖的成功数量为 0。
- 100% 的活动阻塞具有原因和处理人。
- 项目负责人可在两次点击内从总览进入任一阻塞详情。

## 8. 开放问题

- 未完成依赖是否应阻止任务进入“待确认”？当前仅提示，不强制阻止。
